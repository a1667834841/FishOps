

## 🚀 现代项目代码审查规范

### 一、 核心原则 (Core Principles)

1. **友善且建设性**：使用“我们可以...”或“建议...”而不是“你必须...”。
2. **质量守门员**：确保代码符合**健壮性、可读性、可维护性**。
3. **小步快跑**：单个 PR/MR 的代码行数建议控制在 **300 行**以内，超过 500 行应拆分，以防审阅者产生疲劳。

---

### 二、 审查清单 (The Checklist)

#### 1. 业务逻辑与正确性

* **功能实现**：代码是否真实实现了需求？是否遗漏了边界条件（如：空值、溢出、并发冲突）？
* **逻辑简化**：是否有过度设计的嫌疑？是否可以用更简单的逻辑实现？
    - 例如if 判断如果可以提前返回，不要写成if else

#### 2. 安全性 (Security) —— *针对你的 Web 项目重点*

* **输入校验**：SQL 注入风险（尤其是 MyBatis 手写 SQL 时）、XSS 攻击。
* **鉴权与权限**：接口是否做了 Spring Security 或 FastAPI 的权限拦截？
* **敏感数据**：日志是否泄露了用户 ID、手机号或密钥？

#### 3. 架构与设计

* **单一职责**：类、方法是否只做一件事？
* **解耦**：是否使用了依赖注入？是否出现了循环依赖？
* **并发控制**：在处理大量 AI 模型请求或多线程任务时，是否正确使用了线程池、锁或消息队列（如你之前关注的内存队列批量处理）？

#### 4. 性能与资源

* **数据库查询**：是否存在 N+1 问题？查询是否命中索引？（特别是 SQL Server 的死锁预防）。
* **资源释放**：文件流、数据库连接、HTTP Client 是否在 `finally` 或 `defer` 中关闭？
* **内存泄露**：前端 Canvas 监听器是否销毁？Java 中 `ThreadLocal` 是否及时清空？

#### 5. 代码风格与规范

* **命名**：变量名是否具有自解释性？禁止使用 `a`, `b`, `list1` 这种命名。
* **日志**：日志级别是否合适？（`Error` 用于告警，`Info` 用于关键节点，`Debug` 用于排查）。
* **注释**：解释“为什么要这么做”，而不是“这段代码在做什么”。
