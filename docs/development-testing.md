# 项目开发与测试规范

适用于 FishOps-Workbench 及其 Git worktree。功能开发、Bug 修复、测试与交付前读取本规范。按以下顺序执行，每一步保留可核验结果；不能用后续步骤的成功替代前一步验收。

功能实现与 Bug 修复须在定向检查后运行 `npm run regression:full`，覆盖全量单测、类型、构建、产物与真实 E2E 基线。命令、用例和结果边界见[回归测试](regression-testing.md)。真实环境阻碍须报告为待验收，不能仅凭本地通过宣称完整回归通过；纯文档改动仍走 A 路径。

## 0. 按任务风险分路径

先按改动的实际影响初步分级，再选路径；执行中按新证据调整分级。不能仅凭代码行数判断风险。

- **A 微小任务**（文档、错字、不改行为/接口/权限/状态的静态文案）：定向读相关片段 → 修改 → 核对内容一致性与 diff。纯文档变更不运行应用测试、typecheck、build 或浏览器；源码里的静态文案不默认跑 E2E。交付产物仍要构建受影响包；一旦出现布局或行为风险，升级到 C。
- **B 局部低风险逻辑**（错误与输入明确、可单测，不涉及安全、权限、跨系统或外部写入）：定向确认调用契约 → bug 修复前先得到失败回归 → 最小修复 → 补齐相关边界 → 跑必要受影响检查。按真实契约选边界，不加无关用例，不做全仓扫描，不启动浏览器。重复失败、因果不明或影响范围扩大时，先报告新证据并扩大必要诊断；仅出现页面或集成影响时升级到 C，涉及高风险时升级到 D。
- **C 页面、扩展与集成**（DOM、组件、store、路由、扩展 API、初始化等）：从真实入口取证 → 建立失败回归 → 修改 → 相关检查 → 用原流程复测；使用子代理时，优先由同一执行子代理完成该闭环，不按阶段重复派工。遵循现有 `npm run agent:setup` 与外部副作用规范，不遍历全部页面。真实入口不可用时如实标注阻碍，不得用 Mock 页面替代。
- **D 高风险变更**（权限、安全、持久化、迁移、跨系统、删除、真实写入）：先取得明确授权并准备恢复方案，再按实际影响扩大验证范围。

**完成条件**：验收条件和必要检查通过，且没有未解释的失败，即可返回；无关发现记入后续事项。同一错误没有新证据不重复尝试；范围需要扩大时先报告风险。

## 1. 需求与验收目标

1. 阅读 `AGENTS.md`、需求或 Issue、相关代码和现有测试，确认影响范围。
2. 将验收场景写成「用户动作 → 状态变化 → 可见结果 → 副作用」。明确正常路径、边界、再次操作及必要的清理行为。
3. 页面需求明确触发方式、位置、尺寸、图片比例、关闭方式及交互可达性。例如关闭按钮不仅需要可见，还需要鼠标能移到按钮并成功关闭。
4. Bug 先确认根因与影响范围；真实浏览器、扩展或 API 故障先从真实入口读取脱敏运行证据，再建立失败回归。Mock 差异不能单独证明真实故障根因。
5. 关键需求存在歧义、涉及重大架构调整或数据安全风险时，停止并请用户决策。

**完成条件**：验收目标和范围明确，真实副作用边界已确认。新增反馈更新验收目标，并重走受影响的开发、检查、部署和验收步骤。

## 2. 独立工作区与最小开发

1. 从最新主分支建立独立 worktree 与任务分支；已有合适 worktree 时复用。所有修改在该 worktree 内完成。
2. 从 `package.json` 和构建配置查找实际命令、产物目录及运行入口。先读取项目现有脚本，再决定操作方式。
3. 实现最小完整改动，不扩大需求范围或顺便重构。核对调用点、真实运行时输入、状态传递与生命周期清理。
4. Bug 先写失败可执行回归，再修复；需求先补可执行验收断言，再实现。保留失败原因与修复后的结果。
5. 若使用子代理，优先让同一实现代理完成取证、回归、实现、检查及同一入口复测；主代理复核证据。是否使用子代理由 Agent 按任务需要判断；仅在任务独立、无文件冲突且有明确收益时并行，避免重复派工。

**完成条件**：代码覆盖约定行为，失败回归能解释原问题，改动范围可审查。

## 3. 单元测试与开发阶段 Mock

- 纯函数使用真实输入及边界值做确定性测试；Mock 用于隔离网络、Chrome API、计时器及外部写入。
- 类型问题测试真实运行时类型。例如 Vue 数字输入覆盖 `string`、`number`、空值和非法值，而不只依赖 TypeScript 声明。
- 涉及关闭、卸载、监听、在途请求或计时器时，补相应行为回归；计时器使用 fake timer，不依赖长时间真实等待。
- 开发阶段 Mock 页面可用于快速检查布局与交互，但结果明确标为「开发阶段验证」，不计为最终 E2E，不作为 PR 的真实效果图。
- 发布、发送消息和其他外部写入在自动测试中使用 Mock。真实写入仅在用户明确授权该操作后执行。
- 字符串断言检查关键结构，不绑定易变的完整文案。测试数量不能替代验收场景覆盖。

**完成条件**：相关模块测试通过，正常、边界及再次操作可验证；Mock 覆盖范围与真实验证范围分开记录。

## 4. 静态检查与构建

1. 先执行定向回归，再对受影响 workspace 执行必要的全量测试、typecheck 和 build。共享协议或跨包依赖变化时扩大范围；无法隔离时执行全仓检查。
2. 每项检查记录命令、工作目录、代码状态、退出码及结果摘要。长日志保存到本地文件，读取摘要，不因输出截断重复执行。
3. 独立检查可并行，依赖构建产物的验收在构建后进行。最终代码修改后执行检查；代码未变时复用结果，代码或环境变化时重跑受影响检查。检查复用不替代每次 E2E 前的 `agent:setup` 部署要求。
4. 代码交付必须实际构建。单测及 typecheck 不替代 build。
5. CI 已在 `.github/workflows/build-extension.yml` 执行测试、类型检查、构建、安全回归及产物检查；本地通过不代表 CI 已通过，交付时分开报告。

**完成条件**：必要检查退出码为 0，当前代码的实际产物生成成功。

## 5. 真实环境部署与 E2E

### 5.1 部署门槛

1. 确认没有运行中任务，或取得用户允许重载的授权。固定测试目录只供串行验收，多个 worktree 不同时更新它。
2. 每次 E2E 前在**当前 worktree 根目录**运行 `npm run agent:setup`。完成条件是退出码 `0`，且输出包含 `SETUP_COMPLETED`。
3. 该流程负责构建当前代码、同步固定扩展目录、重载扩展与导入本地配置。部署细节读取当前分支的 `docs/agent-testing.md`（如存在）及对应脚本，避免手工复制旧产物或加载其他 worktree 的代码。
4. 当前分支缺少脚本或说明时，报告版本差异并明确脚本来源及适配方案；经授权后补齐或复用现有工具。不得在另一工作区构建后声称验证了当前代码。
5. 部署失败或缺少完成标记时停止 E2E。首次安装、登录及权限问题需要人工介入时，明确说明阻碍。
6. 重载后重新打开真实工作台；涉及闲鱼宿主页时刷新页面以加载新 content script，并确认登录状态。核验实际扩展入口、部署来源与资源版本；配置导入成功不等于业务连接成功。

### 5.2 1:1 验收

- 页面、扩展和集成功能从真实入口，使用真实账号已有数据、真实图片与实际 API 响应，按第 1 节原场景操作。保持同一浏览器任务空间，重载导致旧页面失效时在该空间重新打开页面。
- 最终 E2E 不注入、替换或伪造业务数据，不使用 Mock runtime、Mock 页面或本地 fixture 代替真实系统。无法访问真实环境时标为「待真实验收」，不能宣称完成。
- 按「动作 → 状态 → 可见结果 → 副作用」记录证据。检查再次操作、连续切换、切出再进入，以及涉及变更的尺寸、比例、行高、滚动、关闭与清理。
- 真实数据未包含的边界如实记录，例如没有失败封面或缺失字段；这些场景的单测或 Mock 结果仍属于开发阶段验证，不包装为真实覆盖。
- 只读取必要脱敏信息，不读取或输出 token、cookie、密钥。没有针对具体操作的授权，不执行发布、发送或其他真实外部写入；相应真实路径标记为未验证。
- 若用户接管或结束空间，立即停止。真实入口不可用时确认原因并记录阻碍，不通过换 Mock 入口绕过。

**完成条件**：当前代码已加载，真实可覆盖场景逐项通过，未覆盖项及副作用边界明确记录。

## 6. 页面效果截图

涉及页面视觉或交互效果的 PR，必须附带**最终代码在真实环境中的截图**。

1. 在真实 E2E 中触发目标状态后截图。例如悬浮预览需截图打开状态，新增关闭按钮需在图中可见。
2. 展示需求相关的代表状态；不同布局或行距均受影响时补对应图片。不遍历无关页面。
3. 截图前检查敏感信息，必要时仅裁切或遮盖敏感区域，并说明处理；不替换商品、图片或其他业务内容。截图无法安全公开时先请用户决策。
4. 图片保存到 `docs/images/`，在验收文档和 PR 正文中直接展示，说明真实入口、操作状态及验证边界。GitHub 图片链接指向实际包含截图的提交或稳定可访问资源。
5. 页面代码后续变化时，重新部署、复测受影响场景并替换旧图。Mock 图不得作为最终效果图。

**完成条件**：截图与最终版本一致，PR 内可查看，没有敏感信息，能够直接看出改动效果。

## 7. 自查、Commit 与 PR

1. 自查 diff、需求覆盖、回归范围和文档一致性；运行 `git diff --check`。检查无密钥、无无关改动，未将本地配置提交。
2. Commit、Push，创建关联 Issue 的 PR；已有 PR 时更新该 PR，不重复创建。
3. PR 说明问题或需求、实现方式、关键改动、测试命令与结果、真实验收入口及未覆盖项；页面效果附第 6 节真实截图。
4. 最终报告 Issue、worktree/分支、主要改动、测试结果、Commit、PR 链接及是否需要人工介入。分别说明「已修改、已测试、已构建、已部署、真实验证/待验证」。
5. PR 创建或更新后停止，等待人工 Review，不自动 Merge。

**完成条件**：可审查 PR 已交付，证据和边界清楚，人工 Review 接手。

## 8. 重试与快速路径

- 测试、构建或命令失败先分析原因；最多重试 3 次，每次调整方案。同一错误无新信息时停止。
- 网络、Push 或 GitHub API 异常最多重试 3 次。Git 冲突最多同步主分支并尝试解决 1 次；无法安全解决时停止。
- 需求歧义、重大架构调整、破坏性变更、数据丢失或安全风险、权限/账号阻碍，以及重试后仍失败，均需报告并等待人工处理。
- 纯函数及明确的局部问题在开发阶段可走定向读取、失败回归、最小修复、相关检查的快速路径。功能实现和 Bug 修复交付前仍运行统一完整回归；专项页面验收仅覆盖实际影响范围，不遍历无关交互。
- 纯文档修改只检查内容一致性、链接及 diff 格式，无需应用测试、构建或部署。

- [ ] 独立 worktree/分支，最小修改与必要回归完成
- [ ] 单测与 Mock 结果独立标记
- [ ] 最终代码的必要测试、typecheck、build 通过
- [ ] 需要 E2E 时，当前 worktree 的 agent:setup 成功且包含 SETUP_COMPLETED
- [ ] 真实入口与当前资源版本确认，1:1 场景通过或阻碍明确
- [ ] 页面改动附最终版本真实截图，敏感信息已检查
- [ ] PR 包含实现、测试、真实证据及未覆盖项
- [ ] Commit、Push 与 PR 交付完成，停止并等待人工 Review
