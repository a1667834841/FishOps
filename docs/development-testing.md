# 项目开发与测试规范

本文档适用于 FishOps-Workbench 项目及其 Git worktree，不以目录名区分，其他项目不适用。功能开发、bug 修复、测试和交付前，必须先阅读并执行本规范。

## 0. 按任务风险分路径

先按改动的实际影响初步分级，再选路径；执行中按新证据调整分级。不能仅凭代码行数判断风险。

- **A 微小任务**（文档、错字、不改行为/接口/权限/状态的静态文案）：定向读相关片段 → 修改 → 核对内容一致性与 diff。纯文档变更不运行应用测试、typecheck、build 或浏览器；源码里的静态文案不默认跑 E2E。交付产物仍要构建受影响包；一旦出现布局或行为风险，升级到 C。
- **B 局部低风险逻辑**（错误与输入明确、可单测，不涉及安全、权限、跨系统或外部写入）：定向确认调用契约 → bug 修复前先得到失败回归 → 最小修复 → 补齐相关边界 → 跑必要受影响检查。按真实契约选边界，不加无关用例，不做全仓扫描，不启动浏览器。重复失败、因果不明或影响范围扩大时，先报告新证据并扩大必要诊断；仅出现页面或集成影响时升级到 C，涉及高风险时升级到 D。
- **C 页面、扩展与集成**（DOM、组件、store、路由、扩展 API、初始化等）：从真实入口取证 → 建立失败回归 → 修改 → 相关检查 → 用原流程复测；使用子代理时，优先由同一执行子代理完成该闭环，或按 AGENTS 统一约定不重复派工。遵循现有运行入口与外部副作用规范，不遍历全部页面。真实入口不可用时如实标注阻碍，不得用 Mock 页面替代。
- **D 高风险变更**（权限、安全、持久化、迁移、跨系统、删除、真实写入）：先取得明确授权并准备恢复方案，再按实际影响扩大验证范围。

**完成条件**：验收条件和必要检查通过，且没有未解释的失败，即可返回；无关发现记入后续事项。同一错误没有新证据不重复尝试；范围需要扩大时先报告风险。

## 1. 运行入口

- 优先使用已确认的入口；必要时查 `package.json` 的 `scripts`、`main` 与构建配置，确认 dev 入口和实际 dist 目录。局部校验问题的环境取证可并行进行，不阻塞失败回归与修复。
- 记录刷新方式：改代码后是重跑构建还是热更新，插件与工作台分别如何重载。
- 用户反馈“没生效”时，先确认新代码是否被加载（入口、产物、缓存、重载动作），再排查逻辑。

## 2. 验收场景

- 用“用户动作 → 状态变化 → 可见页面/组件 → 副作用”四段式描述每个场景。
- 按变更行为选择场景：简单输入问题至少覆盖原触发、合法输入、非法/空值和再次操作；涉及初始化、计时、生命周期或导航状态时，再覆盖初次进入、计时结束、切出再进入等对应场景。
- 列表首页不等于展开折叠：首屏加载与逐条展开/收起要分别验证。
- review 按场景逐项复核证据，不以测试数量代替场景证据。

## 3. 行为测试

- bug 修复先建立“失败可执行的复现”，确认复现失败，再修复，再复测通过。
- **真实运行故障闭环**：浏览器、扩展或 API 故障先从真实入口收集 request/response 结构、错误码、`lastError`、耗时及必要后台日志，并核验当前运行入口与资源版本。拿到真实失败证据后，建立失败回归并最小修复；mock 差异不能单独作为 Chrome/SDK 根因证据，也不能代替真实入口验收。无法取得证据时，记录阻碍及已证实/未证实事项。只读取证并脱敏，不读取或输出 token、cookie；发布、发送及其他外部写入仍用 mock，除非取得针对该操作的明确授权。纯函数或明确的本地错误走快速路径，不强制浏览器验收。
- **代理闭环**：是否使用子代理由 Agent 按任务需要判断；使用子代理时，优先由同一执行子代理完成取证、失败回归、修复、相关检查和真实入口复测。仅当任务独立、无文件重叠且有明确并行收益时增加代理；续用原 agent session 与浏览器 space，用户接管时立即停止。
- 类型错误用调用点的真实运行时输入复现，不能只测试 TS 声明或初始字符串 fixture。例如 Vue 的 `type="number"` 配合 `v-model` 会把有效编辑值转为 `number`，应覆盖字符串、数字、空值与非法值，并保留原校验规则。
- 生命周期与倒计时用状态/组件/浏览器测试配合 fake timer 验证，不依赖真实等待。
- 发布与外部写入使用 mock，避免真实副作用，不触达真实发布通道。
- 字符串断言只做结构检查（存在性、关键字段），不断言易变的完整文案。
- 涉及 props、store、controller、订阅或在途请求的变更，核对状态传递与清理；局部纯函数修复不扩展为无关生命周期审计。
- DOM 绑定或集成问题、用户明确要求、或下层测试无法复现时，必须做浏览器验收；纯函数测试足以覆盖的局部问题可按需使用浏览器。外部写入始终用 mock，未做真实环境验证要明确说明。
- 浏览器空间不可用时，确认一次后使用安全隔离环境或报告受阻，不循环探测同一失效入口。

## 4. 验证范围与执行次数

- 先运行失败回归与相关模块测试；最终改动完成后，对受影响 workspace 执行必要的全量测试、typecheck 和 build。共享代码、协议或跨包依赖变更时，扩大到相关包；影响无法隔离时才执行全仓验证。
- 每项大范围检查在最终改动后执行一次；后续修改或检查失败时，重跑受影响检查。独立且无产物依赖的检查可并行，依赖构建产物的验收在构建后执行。
- **检查复用**：记录每项检查对应的代码状态、工作目录和覆盖范围；review 未改动代码时直接复用已有结果，后续仅重跑受影响的检查。检查失败、相关代码变化或运行环境影响其有效性时才重跑。复用不替代第 5 节的交付构建。
- 每条命令返回退出码与结果摘要；输出过长时保存日志并读取汇总，不因截断重复运行。
- 仅修改文档时检查内容一致性与 diff 格式，无需应用测试、typecheck 或 build。

## 5. 构建交付

- 代码变更交付前必须实际构建受影响包；测试与 typecheck 不能代替 build。构建范围按第 4 节确定。
- 用户运行 dist 时，先查现有构建脚本，确认产物写入实际加载目录，并确认新资源已生成。
- 按入口要求刷新或重开工作台，必要时重载插件或刷新宿主页；操作前确认不会打断用户运行中的任务，否则先征得同意。
- 复测原流程；无法运行时明确标注“待用户验证”。

## 完成清单

- [ ] 运行入口与刷新方式已确认
- [ ] 按变更行为选择验收场景，并复核证据
- [ ] 失败复现先行、修复后复测通过
- [ ] 必要测试、typecheck 与 build 已执行（纯文档变更不适用）
- [ ] 代码构建产物已生成；实际加载已确认，或明确标注待验证
- [ ] 按“已修改 / 已测试 / 已打包 / 实际验证或待验证”分层汇报
