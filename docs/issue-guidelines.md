# Issue 规范

本文档适用于 FishOps-Workbench 项目。提交 bug、功能需求或任务前，先检索已有 issue 避免重复，然后统一使用本文档的标题写法与八个章节。GitHub issue 正文与本模板保持一致。

## 1. 标题写法

- Bug：`[Bug] 模块：问题`，例如 `[Bug] 商品库：空数据或未配置时应显示空状态而非扩展处理失败`。
- 功能需求：`[Feature] 模块：能力`。
- 任务：`[Task] 模块：事项`。

模块用中文短名（如“商品库”“聊天中心”“采集”），冒号后一句话说清问题或目标，不超过一行。

## 2. 统一章节

所有 issue 使用同一组章节，按类型适配内容，不新增或改名：

| 章节 | 说明 |
|---|---|
| 问题概述 | 一到两句说清现象与影响。 |
| 环境信息 | 版本、运行环境、相关配置、数据规模、复现频率。 |
| 复现步骤 | Bug 写可复现步骤；Feature / Task 写入口与操作流程，或实施步骤。 |
| 实际结果 | Bug 写当前现象；Feature / Task 写现状。 |
| 预期结果 | Bug 写应有何表现；Feature / Task 写目标。 |
| 证据与排查状态 | 证据来源、已证实事项、排查状态、推测。 |
| 影响范围 | 已知范围与待排查范围。 |
| 验收标准 | 可勾选的验收清单。 |

## 3. 填写规则

- **未知填“待确认”**：无法确定的字段写“待确认”，不留空、不编造。
- **不适用写理由**：某章节不适用时写明原因，例如 Feature 无复现，则“复现步骤”写“不适用：本次为新增能力，入口与操作流程见预期结果”。
- **区分事实与推测**：已证实内容放在证据或实际结果，推测明确标注“推测（待验证）”，不把推测根因写成事实。
- **敏感信息脱敏**：不粘贴 token、cookie、密钥、手机号、订单号、聊天正文等；必要时打码或替换为占位符。截图同样检查是否含敏感信息。
- **检查重复**：先按标题与关键词检索已有 issue，重复则在原 issue 补充，不新建。
- **不擅自分类**：未经确认不使用 label，不擅自指定负责人或里程碑；需要时在正文说明建议。
- **重结果轻过程**：描述以可验证的现象、步骤、结果为主，不堆砌推测的实现细节。

## 5. 按类型适配

- **Bug**：八个章节齐全，复现步骤、实际结果、预期结果必需；“证据与排查状态”写清证据与推测。
- **Feature**：“复现步骤”章节内容填写入口与操作流程（章节名不变），“实际结果”写现状，“预期结果”写目标能力；“证据与排查状态”可写来源与讨论链接。
- **Task**：“复现步骤”写实施或操作步骤，“实际结果/预期结果”写现状与目标；“证据与排查状态”写相关背景与依赖。
