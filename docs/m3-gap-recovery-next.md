# M3 缺口恢复实施边界

日期：2026-10-19。此文档记录当前代码审计结果和后续实施顺序，不是完成证据。

## 当前阻碍不是测试授权

- `chat-sync-service.ts` 的公共结果类型和实现把 `gapCleared` 固定为 false。
- `main.ts::persistChatGap` 只按账号和原因插入存在标记；同原因再次丢失不会产生新的代次。
- `chat-outbox.ts` 持久化账号级 gaps/pageGaps 数组，没有范围、代次或比较后清除接口。
- `page-chat.ts` 的 syncRequired 只增不减，没有可验证的恢复证书入口。
- 群聊和非文本被计为 unsupported，完整翻到末页仍可能 partial。当前不能证明账号级全部历史恢复。

以上是跨进程实现缺口，不能归因于发布暂停，也不能靠再次运行已通过的分页测试关闭。

## 实施顺序

1. 先定义账号、缺口来源、稳定 occurrenceId、generation 和范围的协议。新丢失推进代次，断线重投同 occurrence 不重复推进；旧持久标记按范围未知迁移，不清除。
2. 在页面、outbox、Host 分别持久或保守保留代次；没有可验证页面代次的旧记录保持不可清除。Host 接收不能用到达时间冒充丢失代次。
3. 在同步 run 保存起始缺口快照、文档/socket 身份、覆盖范围和 unsupported 累计。每页数据和进度同事务提交；没有可靠末页或快照边界时不签发证书。
4. 增加覆盖证书与各端确认协议。各端按相同账号/来源/代次/范围比较后清除；部分确认失败时公共 gapCleared 仍为 false。新缺口不能被旧证书清除。
5. 全局范围未知的缺口需要完整会话列表及所有相关历史覆盖；当前不支持的群聊/非文本、平台删除/保留窗口或不稳定快照使覆盖不可证明时，返回明确未覆盖原因，不做自动无限扫描。

## 必须的行为验收

- 同一 occurrence 重投不推进代次，新 occurrence 即使原因相同仍推进。
- 旧证书遇到新代次不清除；其他账号和会话不能相互清除。
- 单会话完成不清全局缺口，只有会话列表完成也不清消息缺口。
- 第 k 页失败保留前 k-1 页，Host 重启不发平台请求；证书重投幂等。
- 页面/outbox/Host 任意端清除失败，仍明确报告未完全恢复。
- unsupported、未知范围、删除历史、分页边界不明均不能伪造无损。
- 成功证书、完成状态与恢复事件事务落盘后才发送 SSE 通知。

真实发布仍暂停，与本缺口的代码实施无关。不得通过删除契约、固定返回 true 或直接删 state 标记完成验收。

## 生产接入顺序与失败关闭要求

- 第一阶段仅新增纯协议结构与比较函数，不导入公共 METHODS，不新增 API 清除入口，也不接入真实清除。外部自称 complete/ack 的布尔值不能成为可信恢复证据。
- 第二阶段让页面产生稳定缺口 occurrence，经 collector/outbox 保留身份，替换现有 `chat-gap` 只有 reason 的消息；新旧帧兼容时，旧帧只能建立范围未知且不可自动清除的缺口。
- 第三阶段在 Host 同一事务中登记 occurrence、代次和事件；重新连接重投同一 occurrence 不得推进代次。禁止把每次 flush 当作新丢失，也禁止将同原因的全部丢失合并为同一代次。
- 第四阶段接入同步覆盖记录与恢复协调器。证书只可由持久已提交 run 及固定范围推导，不接受调用方直接上传一个声称已覆盖的证书。比较函数返回 true 只是必要条件，不是清除权限。
- 第五阶段页面和扩展确认必须绑定当前文档/存储代次，Host 只有全部必要端确认后才报告恢复。跨端提交不是 SQLite 单事务，需持久阶段机及幂等恢复，失败维持缺口。

当前生产帧 `chat-gap`、`OutboxState.version=1` 和页面 `syncRequired` 均没有这些字段；基础模块测试通过不意味着端到端完成。Orca 阶段同步尝试失败，原因是 Orca 未运行，不能记为已进入 done。

## 2026-10-19 当前接入进度更新

前文各阶段审计按历史保留；以下为当前代码状态，替代“尚未接入”的旧描述：

- 页面提供按账号隔离的最近 unknown 缺口身份，固定文档来源经 collector 写入 outbox；旧页面走旧标记路径。
- outbox 容量丢失生成稳定身份、来源代次和会话范围；同消息重投去重，元数据有界，耗尽失败关闭。
- native 新帧携带 occurrence，校验外层账号/原因一致；旧帧兼容且不用于恢复授权。Host 生产回调使用账本，并将新缺口事件与账本原子提交。
- 同步 run 起始保存 Host 账本快照；每页在数据提交事务中累计 unsupported 数量、末页事实和固定文档身份，并携带到下一页预留。旧 run 没有该记录时不补造覆盖事实。新增行为用例验证期间出现新缺口不会改写起始快照，重建服务后 unsupported 仍累计。
- 此快照仅含新账本，不覆盖旧 state 标记，也不证明页面/outbox 无未送达缺口。`terminal` 只是平台返回末页，不是可靠快照、历史保留范围或恢复证书。当前仍不签发证书、不清任何标记。

剩余关键实现：可信覆盖边界与旧缺口迁移判定、三端比较确认、持久恢复阶段机、真实页面/浏览器 E2E。unknown 范围在缺少全覆盖证据时必须继续报告未恢复，不能因末页而转绿。

### 新旧通知分流修正

outbox 增加可选 `legacyGaps`，区分旧无身份告警与新 occurrence。新空存储初始化为空，只有旧格式加载和显式 `markGap` 才建立旧标记；新 recordGap/容量丢失不额外制造旧标记。连接仅在存在 legacyGaps 时发送兼容帧，稳定事件单独投递。旧存储没有该字段时保守将原 gaps 视作旧标记，不推断已被新事件覆盖，也不删除 Host 既有 state。

25 项 outbox/连接定向检查、类型检查与构建通过，包括新身份跨重建不产生旧通知、旧状态迁移、显式旧通知保留和账号隔离。此为避免继续制造双源的修正，不是已有历史双源的恢复迁移，也不是清除完成。尚未部署本修正，不复用旧真实浏览器证据。

### 缺口记录失败与正常消息交付解耦

collector 仍先尝试持久缺口；若缺口写入失败，保留错误并继续正常消息的逐条持久化及确认，最后抛出原缺口错误。只有成功持久化的消息会 ACK；消息写入或 ACK 失败仍立即停止，后续项保留。页面缺口不清除，下次采集仍重试同身份。

这修正“缺口元数据耗尽导致正常消息永久阻塞”的退化路径，不把失败转成成功，不删除已有元数据。13 项 collector/固定文档来源/native管道检查、类型检查及构建通过。历史日志中“缺口写失败不ACK任何消息”的描述为旧行为；当前允许已独立持久成功的正常消息 ACK，但缺口本身绝不确认恢复。尚未部署该修正。
